# Repository review and Streamlit demo readiness

Reviewed baseline: `bd156f84760ad8c800895097a42e1a07a04a3705` (100 tracked files; 94 Python files). Review date: October 23, 2026.

## Assessment

The repository has a usable, bounded scene-drafting workflow and substantial validation logic. It was not deployable from a fresh checkout: all six specialist agents and the live draft adapter import a missing `config.py`, there was no Streamlit entry point, and several legacy test fixtures predate the newer source-passage contract.

The changes in this delivery provide a Streamlit demo around `workflows/draft_writers_room.py`. The app is validated offline and starts successfully on Python 3.12. Live generation and public hosting still require a smoke test with the owner's credentials. The larger research/audit pipeline is not certified as production-ready by this review.

Scope: repository-wide syntax/import/dependency inventory; targeted inspection of generation, evidence, provider, orchestration, retry, checkpoint, and evaluation boundaries; execution of the focused tests and standalone script inventory; implementation and testing of the demo. This is not a claim of an exhaustive formal audit of every line or model-generated behavior.

## What the demo does and does not prove

The actual draft workflow validates input, generates provisional Character notes, then generates one scene. It enforces exact requested character identities, a bounded reference context, known reference IDs, complete model responses, valid output schemas, and a maximum of two provider requests without automatic retry or repair. It labels the result unverified.

Those checks cannot establish canon accuracy, character voice quality, semantic support for a citation, chronology, or fulfillment of every creative instruction. The demo does not run Memory Alpha retrieval, the Story Architect, semantic grounding audits, Continuity, or Evaluation. It makes this scope visible in the interface and exports.

Uploaded source hashes provide integrity checks, not signatures or proof that the uploader retrieved authentic material. Uploaded content remains untrusted reference data. The built-in sample has no reference claims and is explicitly an illustrative authored scene, not a historical model run.

The public sample uses no credentials or provider quota. Live drafting requires configured host credentials, a host-defined access code, and an acknowledgment. A process-wide lock prevents overlapping live submissions; a per-session cooldown limits accidental repeated clicks. These are not durable global rate limits or a billing guarantee. Provider quotas still apply, and the host should keep the access code private.

## Legacy failures requiring follow-up

Nine scripts use old Lore fixtures or expectations without valid source packages:

- `workflows/artifact_material_change_regression_test.py`
- `workflows/evidence_refresh_regression_test.py`
- `workflows/evidence_refresh_commit_regression_test.py`
- `workflows/evidence_refresh_checkpoint_regression_test.py`
- `workflows/evidence_resolution_orchestrator_regression_test.py`
- `workflows/writers_room_scriptwriter_test.py`
- `workflows/writers_room_full_integration_test.py`
- `agents/Evaluation Test Files/evaluation_lore_adapter_test.py`
- `agents/Evaluation Test Files/evaluation_production_manifest_test.py`

For example, `lore_result()` in the material-change regression constructs a `SimpleNamespace` containing support flags and a summary, but no `evidence_package`. The current snapshot builder deliberately treats that legacy artifact as non-authoritative. The test then incorrectly expects changes in the summary to count as changes in authoritative evidence. The integration tests similarly attempt to route “supported” Lore without a source package and correctly encounter `LoreEvidenceContractError`.

Repair these fixtures using explicitly synthetic source packages and preserve negative tests proving that legacy summaries are rejected. Do not relax the production source contract simply to obtain green legacy tests. Re-run the complete affected suites after fixture migration; their first failing assertions may currently hide additional issues.

Two diagnostic failures have separate causes:

- `agents/Scriptwriter Test Files/scriptwriter_audit_batch_diagnostic_test.py` imports `scriptwriter_self_repair_integration_test` from `agents`, but that module is now inside `Scriptwriter Test Files`.
- `agents/Scriptwriter Test Files/scriptwriter_repaired_scene_reaudit_test.py` depends on `runtime/diagnostics/scriptwriter_failure_e08190355ed44fcab94ad127b156f539.json`, which is intentionally not tracked.

The 15 blocked live scripts are not scored as passing or as evidence of a provider regression. They need deliberate live validation when quota is available. The full inventory follows.

## Reproduce the review

From an environment with `requirements-dev.txt` installed:

```powershell
python -m pytest -q
python run_draft_scene.py
python scripts/review_legacy_tests.py
```

The third command blocks HTTP and socket access, substitutes dummy credentials, runs each legacy script in a separate process, and writes its report beneath ignored `runtime/diagnostics/`. It exits nonzero while deterministic legacy failures remain. It is diagnostic tooling, not a substitute for the default CI suite or a live acceptance run.

## Completion criteria for the hosted demo

1. Apply the delivered patch and push the resulting commit.
2. Deploy `app.py` on Streamlit Community Cloud using Python 3.12. Verify the illustrative sample opens without secrets.
3. Add Cloudflare credentials and a demo access code through Streamlit Secrets. Keep these values out of Git and chat.
4. Generate one default scene and verify that it shows two attempted provider requests, an unverified review status, and working Markdown/JSON downloads.
5. Review the scene manually for chronology, character voice, fictional allegations, and the prohibited assumptions. A successful response is not automatic canon certification.

Only after this smoke test should the live demo be described as verified on the owner's account. Before exposing the full production workflow, migrate legacy fixtures, repair diagnostic portability, introduce a global model-call/token budget, and verify retrieval under deployment conditions.
